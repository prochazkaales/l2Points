# Část 7 – Azure: plán implementace

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Aplikace běží v Azure Container Apps nad Azure SQL a každý push na `main` ji po testech a smoke testu image sám nasadí.

**Architecture:** Aplikace dostane úpravy pro provoz za proxy v Azure (zámek startu na SQL Serveru, šifrování Data Protection klíčů v Key Vaultu, health live/ready, konfigurovatelné forwarded headers). Infrastruktura je jeden Bicep soubor, který jednorázově (a při změnách infra) spouští uživatel skriptem `infra/deploy.ps1`. GitHub Actions dělají build + testy, sestavení image a smoke test proti SQL Serveru v kontejneru, push do GHCR a `az containerapp update` přes OIDC.

**Tech Stack:** .NET 10, EF Core 10 (SQL Server), Azure Container Apps, Azure SQL Basic, Key Vault, Log Analytics, Bicep, PowerShell 7, GitHub Actions, GHCR.

**Spec:** `docs/superpowers/specs/2026-10-29-azure-deployment-design.md` (doménová pravidla dál podle `docs/superpowers/specs/2026-10-28-l2points-design.md`).

Větev: `feature/azure` (už existuje, obsahuje commit se specem).

- Azure SQL Database `Basic` (5 DTU, 2 GB). Smíšená autentizace: SQL login pro aplikaci + Entra admin = účet, který spouští `deploy.ps1`.
- Budget na `rg-l2points` 20 USD měsíčně, upozornění při skutečné útratě 80 % a 100 % a prognóze 100 %, e-mail jako parametr.

## Review Focus

1. Opakované spuštění `deploy.ps1` nad existujícím prostředím nesmí změnit hesla, super admina (login, nick), běžící image ani budget. Hlídá Task 5 (logika „initial vs. update“) a ruční ověření v Rolloutu (krok R6).

4. Liveness nesmí záviset na DB (výpadek DB nesmí restartovat kontejner), readiness ano. Smoke test v Task 4 ověří `/health/live` i `/health/ready`.
5. Workflow bez nastavených Azure proměnných (před prvním zřízením) musí deploy přeskočit a skončit zeleně; push na PR nesmí nic publikovat ani nasazovat. Podmínky v Task 4, ověření v Rolloutu (R2).

## Rollout (dělá controller s uživatelem, ne subagent)

- [ ] **R1:** Uživatel potvrdí veřejné repo a force push. `git remote add origin https://github.com/prochazkaales/l2Points.git`, `git push --force -u origin main` – až po merge `feature/azure` do `main` (po final review a souhlasu s merge), nebo push větve `feature/azure` dřív, pokud chceme CI ověřit před merge (build-test běží na všech větvích, image/deploy jen na `main`).
- [ ] **R2:** Ověřit běh workflow na GitHubu (stránka Actions v prohlížeči, `gh` není): build-test zelený, image + smoke zelený, deploy přeskočený. Při chybě opravit, commit, push. Po úspěchu odstranit TODO v Dockerfile, pokud zbylo.
- [ ] **R3:** Uživatel přepne balíček `l2points` v GHCR na veřejný.
- [ ] **R4:** Uživatel v terminálu: `az login` (účet s VS předplatným), `pwsh infra/deploy.ps1 -SubscriptionId <id>`, zadá login, nick, heslo, e-mail.
- [ ] **R5:** Uživatel nastaví GitHub variables; controller spustí deploy (prázdný commit nebo re-run workflow) a ověří zelený deploy.
- [ ] **R6:** Ověřit aplikaci na `appUrl`: `/health/ready` 200, přihlášení super admina (uživatel), přihlášení přežije další nasazení (ověřuje DP klíče v Key Vaultu). Uživatel spustí `deploy.ps1` podruhé – nic se nezmění (image, super admin, heslo platí dál).
