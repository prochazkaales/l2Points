# Část 5 – Šperky: implementační plán

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Evidence epických šperků: typy šperků se seedem a herními ikonami, stránka **Šperky** (`/jewels`, počty kusů a držitelé), ikony šperků u nicku v Přehledu a Týden – všichni, sekce šperků v Detailu hráče a admin stránka **přiřazení / odebrání** (`/admin/jewels`).

**Architecture:**
- Entity `JewelType` a `UserJewel` a čisté seskupení (šperky po hráčích, galerie) jsou v `L2Points.Domain/Jewels`. Statistiky (`Stats`) o šperkách nevědí.
- Persistence: konfigurace, migrace `AddJewels`, seed typů v `ReferenceDataSeeder`, dotazy v `JewelQueries`. Nová `JewelService` (galerie, admin přehled, přiřazení, odebrání).
- `OverviewService` a `PlayerStatsService.GetPlayerDetailAsync` navíc vrací `JewelsByPlayer` (mapa UserId → šperky). Typ řádků `LeaderboardRow` a řadicí funkce se nemění.
- Buňka s nickem se sjednotí do sdílené komponenty `PlayerNickCell` (odkaz, čip „neaktivní“, ikony šperků) a sdílené CSS pro přilepený sloupec jde do `wwwroot/app.css`.

**Tech Stack:** .NET 10, Blazor Interactive Server, MudBlazor 9.x, EF Core 10, xUnit, `FakeTimeProvider`.

**Spec:** `docs/superpowers/specs/2026-10-28-l2points-design.md` (§3.6, §3.7 mazání hráče, §4 body 4–6 a 8 „Šperky“, §5.2) · Roadmapa: `docs/superpowers/plans/2026-10-28-00-roadmap.md` (Poznámky – Část 5) · Konvence: `CLAUDE.md`

## Global Constraints

- UI je česky, kód, komentáře a commity anglicky. Commit končí prázdným řádkem + `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Typy šperků (seed, v tomto pořadí `SortOrder` 1–8), `Code` → `Name`:
  `QueenAntRing` → „Ring of Queen Ant“, `CoreRing` → „Ring of Core“, `OrfenEarring` → „Earring of Orfen“, `ZakenEarring` → „Earring of Zaken“, `FrintezzaNecklace` → „Necklace of Frintezza“, `BaiumRing` → „Ring of Baium“, `AntharasEarring` → „Earring of Antharas“, `ValakasNecklace` → „Necklace of Valakas“.
- `ImagePath` = `images/jewels/{Code}.png` (relativně, `<base href="/">`). Ikony jsou už v repu: `src/L2Points.Web/wwwroot/images/jewels/*.png`, 32×32 PNG z l2j.ru.
- Hráč může mít víc šperků, i stejného typu. **Bez data.** Odebrání odebere jeden kus.
- Všichni přihlášení vidí počty a držitele. Přiřazení a odebrání jen role Admin (stránka `[Authorize(Roles = Roles.Admin)]`).
- Mazání hráče kaskádově maže `UserJewel` (FK `UserId` → `AspNetUsers`, `Cascade`). FK `JewelTypeId` je `Restrict`, typy se nemažou.
- Seed přidá jen chybějící typy (podle `Code`), existující nikdy nepřepisuje.
- Šperky neaktivních hráčů se počítají do kusů v partě. Držitel je označen „neaktivní“.
- Pořadí: typy podle `SortOrder`, pak `Id`. Držitelé podle nicku `StringComparer.OrdinalIgnoreCase`, pak `UserId` `Ordinal`.
- Více kusů stejného typu u hráče = jedna ikona s „×N“. Popisek ikony (`title`, `alt`) = název šperku, u N > 1 „Název ×N“.
- DB přístup jen přes služby (`IDbContextFactory`). Žádný `AppDbContext` v komponentě.
- Mobil (375 px): nick má `max-width: 8rem`, ikony šperků se zalamují pod nick. Dark i light.

## Rozhodnutí tohoto plánu

- `Activity.JewelTypeId` (spec §5.2 „informativní“) se **nezavádí**: název šperku bosse jasně pojmenovává a seed by u existujících aktivit vazbu stejně nedoplnil. YAGNI.
- Admin přiřazení je samostatná stránka `/admin/jewels` (výběr hráče, u každého typu počet a tlačítka −/+). Zbytek adminu přijde v části 6, `AdminHome` dostane odkaz.
- Služba nekontroluje roli: volá ji jen admin stránka, jejíž autorizace běží na serveru (Blazor Server). Část 6 může přidat obecnou kontrolu.
- Detail hráče má sekci **Šperky** (čipy ikona + název + ×N), protože na mobilu `title` nefunguje. Hlavička detailu zůstává bez ikon.
- V Událostech týdne (čipy účastníků) se ikony nezobrazují, aby seznam zůstal kompaktní.

## Review Focus

1. **Dva kusy stejného typu** u jednoho hráče → jedna ikona „×2“, v galerii se počítají kusy (ne držitelé) → test v Task 1.
2. **Odebrání, když hráč šperk nemá** (dvojklik, zastaralé UI, druhý admin) → `NotHeld`, žádná výjimka, UI se znovu načte → test v Task 3, UI v Task 6.
3. **Neexistující hráč nebo typ** při přiřazení (hráč mezitím smazán) → `UnknownPlayer` / `UnknownJewelType` bez zápisu → test v Task 3.
4. **Chybějící soubor ikony** (překlep v `Code`/`ImagePath`) → každý seedovaný `ImagePath` existuje ve `wwwroot` → test v Task 4.
5. **Smazaný hráč** → jeho šperky zmizí s ním, typ zůstane → test v Task 2. **Neaktivní držitel** se počítá a je označen → test v Task 1.
